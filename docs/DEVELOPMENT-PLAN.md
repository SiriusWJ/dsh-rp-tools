# dsh-rp-tools 分层注入与会话面板改造计划

> **⚠️ 历史设计记录（已作废，勿照做）。** 本文是当时针对**会话级生图配置**写的一份分层注入与面板改造设计，
> 改造本身早已落地；而它服务的那些设置（会话默认风格 / 风格备注 / 生图开关）已在 **v1.15.0 随本地生图链路一起移除**。
> **正文保持原样**，只作历史记录阅读 —— 用来理解「当时为什么这么设计」，不要照着实现。
> 现状与变更见 `docs/REMOVE-IMAGE-GEN.md` 与 `docs/STATUS.md` §7 变更历史。

## 1. 背景与目标

本计划针对测试会话 `D:\Story\rp-sessions\6c0d92ff-6318-4d26-9adb-4e8680174059` 暴露的问题，完成以下六项经确认的改造：

1. 采用混合分层注入：DM 行为规则和紧凑会话清单进入 system standing；世界书事实、当前状态和活动人物详情进入 runtime context；卡全文和开场白保留为文件。
2. 开局消息只发送一个解析后启动文件地址，不内联大段开场白，也不默认触发全量“设定整备”。
3. 导入时自动识别并填充 DM 设定；同时让 DM Agent 能通过正式工具修改同一份 DM 配置。
4. 检测世界书 key 与人物卡 key 的重合，提示 DM 不要重复注入，并在装配层阻止重复正文进入上下文。
5. 角色卡与世界书默认只占一行；详细配置改用较大的浮窗编辑器。
6. 将“生图配置（本会话）”移动到 RP 面板最上方，与生图开关、首次出场、重要场景等设置合并。

## 2. 已确认的根因

- 导入器把无 keys 的世界书条目全部补为 `constant`，而解析器本来已经支持用标题作为默认触发 key；测试会话因此出现 26 个顶级条目全部常驻。
- `renderConstantLore()` 没有总字符预算，外部卡片正文被大量放入 system standing。
- 世界书解析器把 `##` 到 `######` 都视为新条目，而编辑/合并逻辑只把精确 `## ` 当边界；同一文件顶级条目 26 个，运行时曾解析成 35 个。
- 《爱情公寓》卡同时包含 DM 规则、多人世界书和开场白，但现有互斥布尔分类把它误判成单一角色“爱情公寓”，导致 `dm.prompt` 为空。
- 当前会话有 15 张人物卡，同时世界书仍保留相同 15 个人物全文；角色被提及时可能发生双重注入。
- `writeImportFiles()` 读取不存在的 `built.greetings`，导致导入结果显示 5 条开场白，但 `.opening.md` 实际写成 0 条。
- 第一轮开局消息内联开场白并附带全量整理任务，测试会话产生 10 个模型步骤、29 次工具调用和约 954,658 个未缓存输入 token。
- 会话存储和 UI 已有 `dm.prompt`，但 `rp_session` 工具没有修改 DM 设定和本会话生图策略的参数。

## 3. 目标架构

### 3.1 注入分层

#### System standing

只允许以下内容进入：

- 通用 DM 运行规则；
- 用户确认后的 `session.dm.prompt`；
- 战役名、简短世界总纲；
- 紧凑人物索引；
- 世界书文件、启动文件等路径指针；
- 一行结构化生图策略；
- 用户手动提升的少量核心事实。

约束：

- 外部导入世界书不得因 `constant` 自动获得 system 权限；
- system standing 设置总字符预算；
- 超预算内容降级为 runtime/on-demand，而不是截断成残句。

#### Runtime context

按优先级注入：

1. 当前状态；
2. 在场人物详情；
3. 最近对话明确提到的人物详情；
4. 命中 key 的世界书条目；
5. 用户明确固定但未提升到 system 的条目。

人物与世界书分别设置条数和字符预算。注入规划阶段按来源 ID/内容指纹去重，保证同一正文最多出现一次。

#### 文件与按需读取

以下内容不常驻注入：

- 原始卡片全文；
- 所有备用开场白；
- 被预算挡下的世界书正文；
- 导入映射与来源记录。

### 3.2 多标签导入计划

废除“DM 卡或角色卡”的互斥二分，改为一次导入可以同时拥有：

- `hasDmRules`
- `hasPrimaryCharacter`
- `hasLore`
- `hasRuntimeState`
- `hasOpenings`

导入器生成可预览的 typed import plan：

- `dmRules[]`：来源优先级为 `system_prompt`、`post_history_instructions`、description/personality 中的主持规则、规则型世界书条目；
- `characters[]`：从具名人物条目中提取；
- `lore[]`：世界观、地点、势力、历史、规则事实；
- `initialState[]`：日程、足迹、当前好感、当前物品等会过期信息；
- `openings[]`：开场白及选中项；
- `warnings[]`：不确定分类、重复 key、超预算和结构错误。

每项保存来源卡指纹、原条目 ID 和正文指纹，支持幂等重导、去重和迁移回滚。

### 3.3 key 与重复检测

统一规范化 key：去首尾空白、统一大小写、全半角和常见标点；保留原文用于展示。

检测范围：

- 人物卡名称、别名和索引名；
- 世界书标题和显式 keys；
- 同一卡片重复导入的来源 ID/正文指纹。

行为：

- 导入预览与 RP 面板显示“与人物卡重复”警告；
- 提醒 DM：人物专属正文应放人物卡，世界书只保留跨人物/世界事实；
- runtime 注入时若世界书条目 key 命中已展开人物，则跳过重复人物正文，并在诊断信息中记录原因；
- 不仅按标题删除，避免同名地点/人物被误伤；优先使用来源映射与正文指纹。

## 4. 开局流程

导入完成后生成一个小型 `cards/<slug>.launch.md`，包含：

- 选定开场白及其来源；
- 世界书、卡全文、备用开场白文件路径；
- 已写入的 DM/人物/世界/状态摘要；
- 尚需人工确认的警告；
- “开始剧情但不要复述文件”的明确指令。

自动发送的首条消息限定为：

```text
【开局】请读取 rp-sessions/<session-id>/cards/<slug>.launch.md，按其中“选定开场”开始；不要复述文件内容。
```

删除默认 `buildTidyPrompt()` 串联；保留“智能整理”为用户显式点击的可选操作。

## 5. DM 设置

- 修复 DM 规则检测，覆盖“扮演除玩家以外所有角色”“讲述者/Narrator”等表述，以及 `system_prompt`、`post_history_instructions`。
- 使用“第一个非空字段”而不是 `??` 处理空字符串回退。
- 导入预览展示将写入 `dm.prompt` 的来源片段，用户确认导入后直接落盘。
- 扩展 `rp_session(action:"set")`，支持 `dm_prompt`、`images_enabled`、`images_first_appearance`、`images_key_scenes`。
- RP 面板和工具共用同一份会话配置，Agent 修改后面板软刷新即可看到结果。

## 6. 会话面板 UI

### 顶部：本会话生图

RP 标题下第一块固定为紧凑控制条：

- 自动配图总开关；
- 首次出场；
- 重要场景；
- 会话默认风格；
- 试出/预览；
- 高级配置入口；
- 已有立绘数量摘要。

移除面板底部重复的会话生图配置块。

### DM 设定

默认显示一行摘要：“已配置/未配置、字符数、来源、编辑”。长文本使用浮窗编辑。

### 角色卡

默认单行包含：名称、brief、立绘/完整度标记、常驻开关、编辑、删除。点击编辑后用大浮窗展示完整字段与立绘。

### 世界书

默认单行包含：标题、类别、keys/constant/order、字符数、重复提示、编辑、删除。点击编辑后用大浮窗编辑元数据和正文。

### 浮窗

使用 React portal 挂到页面根级，建议宽度 `min(1100px, 85vw)`、高度 `min(860px, 85vh)`；支持 Esc、焦点恢复、未保存确认和固定保存栏。

## 8. 验收标准

针对《爱情公寓》测试卡与测试会话：

- 识别为“含 DM 规则 + 世界书 + 多人物”的组合卡；
- `dm.prompt` 非空，不创建名为“爱情公寓”的人物；
- opening 文件实际包含 5 条开场白；
- 世界书顶级条目和运行时解析条目数一致；
- 15 个主要人物成为 15 个 canonical 角色卡，人物正文不再从世界书重复注入；
- 无 keys 条目默认使用标题触发，不自动 constant；
- 首条开局消息少于 500 字，只含 launch 路径和启动指令；
- 默认开局不再触发全量角色搬运和世界书编辑；
- 同一正文指纹在一次装配中最多出现一次；
- RP standing 相比测试基线 38,556 字显著下降，且不含未经确认的外部世界书全文；
- RP 面板顶部显示完整会话生图控制，人物和世界书默认均为一行；
- 所有自动化测试通过，已有非 DM 会话仍看不到 RP 工具和界面。

## 9. 数据安全与迁移原则

- 原始 PNG、卡全文和导入 JSON 永远保留；
- 现有会话不做静默破坏性迁移；
- 迁移先输出分类、移动、跳过和冲突清单；
- 支持备份原会话 JSON 与世界书；
- 任何无法确定归属的条目保留原位并标记待确认，不让 Agent 自行猜测删除。
